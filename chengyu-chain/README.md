# 成语接龙 chengyu-chain

面向小朋友的独立语音应用，当前版本 0.2.0。机器人先出成语，用户接末字或同音字，不分声调，也允许 an/ang、en/eng、in/ing 的前后鼻音差异，例如“画龙点睛”接“斤斤计较”。LLM 判断成语及意图；程序校验完整同音转写和两段接龙，维护输赢及期限。

初级、中级、高级分别使用常见、较少见和更生僻的机器人成语，每局接对 5、7、10 次获胜。本局累计三次明确识别为真实成语但接音错误的回答判负；没听清、非成语、判断不确定和模型失败均不扣次数。获胜后询问是否挑战下一级，高级通关后可从初级再来；失败后可重玩同级，结束一局不会退出应用。

可以说“难一点”“降低难度”“解释一下”“给我提示”。手动换级重新计分，解释与求助不加分。同音错字经本地逐字拼音验证后可以接收，机器人会明确复述规范词；缺字、候选歧义不能靠模型猜测补全。成语真实性及多音字语境仍需模型判断，现场识别准确率须另行对照验证。

## 安装与配置

需要 Python 3.10–3.12、目标机已安装的 ROS 2 / `rclpy` / `aimdk_msgs`、原厂语音前端与媒体服务。沿用机器人消息包，不用本地 SDK 替换它。独立程序不依赖 Buddy 或点歌台安装。

Q1 的消息包须与当前固件匹配。Buddy 托管启动会成套加载 `/robot/software/interface/aimdk_msgs` 的 Python 包、C 类型库与 ament 路径；独立运行也须使用同一套环境。当前 `GetMcMotions` 请求包含 `form_state`，旧 housekeeper 消息包缺少该字段，会被明确拒绝，不尝试发送动作。模式管理子进程同样选择当前接口库，并在发现稳定、只读握手成功后才写模式；正常或异常退出仍须确认原模式恢复。此次兼容性修复不需要升级机器人固件。

```bash
python3 -m pip install -r requirements.txt
python3 main.py --check
python3 main.py configure
python3 main.py check-models
```

安装向导沿用 Buddy 的分步边框和方向键菜单风格，依次优先采用游戏已有配置、Buddy 已保存且受支持的配置、手动输入。回车保留选项，Key 隐藏输入；取消后恢复终端并保留原配置。首版支持千问北京地域和对应业务空间域名，模型列表由向导列出。确认后写入游戏自己的 600 权限 YAML；Buddy 以后修改模型或 Key 不影响游戏。运行时不使用通用环境变量中的 Key，不回退到 Buddy 模型。

音色菜单按模型显示官方中文名称，例如“龙安灵心”“许南川”“龙泡泡”“龙牛牛”，仅列出当前模型实际支持的项目，仍可填写自定义 ID。切换 TTS 模型时推荐匹配的默认音色；模型未变时保留已有自定义音色。例如 3.0 Plus 使用 `longanlingxin`，3.1 Plus 使用 `longanlingxin_v3.1`。自定义音色也必须与模型匹配，详见[官方音色列表](https://help.aliyun.com/zh/model-studio/qwen-audio-tts-voice-list)。

`configure` 还调用自有 TTS，缓存一句结束播报供断网退出使用，不播放音频。若缓存失败，配置仍保留，可联网后执行 `python3 main.py prepare-audio`；有效缓存是开局预检条件。`check-models` 分别实际调用 ASR、LLM、TTS，只有各项检查通过才说明对应云调用成功，检查不会播放声音或动作。

默认私有目录为 `~/.chengyu-chain/`，其中 `config.yaml` 是配置，`ending.wav` 是缓存播报，`runtime/` 是锁和恢复记录。可通过 `CHENGYU_DATA` 或显式参数选择位置；公共路径参数放在子命令前：

```bash
python3 main.py --config /path/config.yaml --data-dir /path/data --runtime-dir /path/runtime status
```

重新安装保留配置与数据；源码示例没有真实 Key。

## 播音词配置

只开放四项常用台词：答对鼓励、获胜赞美、升级邀请、失败安慰。其他阶段提示固定在代码里，安装向导不增加填写步骤。每次答对会说明本局进度；第5/7/10次获胜后明确赞美并邀请下一局，等用户说“继续”才开始。计分与换局由程序控制，LLM负责成语和解释。

修改游戏自己配置的 `speech`，下一次开局生效；只填写需要改的项目，未填写的使用默认值。Buddy安装位置为 `~/.primebuddy/cfg/skills/chengyu-chain/config.yaml`，独立安装为 `~/.chengyu-chain/config.yaml`。不要用无Key示例覆盖已有配置。

```yaml
speech:
  correct: '接对啦，真棒！本局已接对{successes}次，目标是{target}次。我接“{next_idiom}”。'
  win: '太棒了！你已经接对{target}次，赢得了{level}挑战！'
  win_next: '我们提高难度，挑战{next_level}吧！准备好了就说“继续”。'
  lose: '这局没能过关，没关系，下次再试！'
```

占位符含义：`successes`是本局正确次数，`target`是通关目标，`next_idiom`是机器人的接词，`level`是当前级别，`next_level`是下一级。每项只允许示例所列的字段，文字不可为空、超过400字或包含格式表达式。接字提示、失败后重玩邀请、高级通关后回到初级的邀请由程序补上，无须重复写入。配置只改话术，不改变规则；重新运行向导会保留自定义台词。完整示例见 [cfg/config.yaml](cfg/config.yaml)。

## 运行与退出

在支持技能包模式声明的 Buddy 中安装本技能，再说“开始成语接龙”。本技能的 [cfg/pkg.yaml](cfg/pkg.yaml) 已配置 `primebuddy.mode: exclusive` 和 `primebuddy.cli` 启动、状态、恢复命令，Buddy 读取后统一处理整局交接，无需增加技能名专用映射。普通技能未声明模式时默认为 `task`。[宿主协议](references/buddy.md) 说明了整局前台进程、资源核验和新的语音轮次。已发布的 Buddy 1.1.0 需要更新宿主代码，不能只复制技能目录后假定具有独占能力。

独立运行时，先退出 Buddy 语音会话，并加载实际控制板的原厂 ROS 环境，然后执行：

```bash
python3 main.py check-play
python3 main.py play --manage-agent
```

`--manage-agent` 会设置原厂 `only_voice`、启停原厂 Agent 使模式生效，退出时恢复原模式。此参数仅供知情操作者独立使用，运行前需确认可以中断原厂语音。默认不开身体动作；显式启用且通过站立路径验收时，可以在开局前准备站立，详见下方动作说明。宿主通过 `play --hosted` 运行时不做这些模式操作。

同一控制器通过 `/tmp/primebot-voice-frontend.lock` 互斥独立游戏与新版 Buddy。跨板运行仍需固定唯一应用板；本地文件锁不能协调两个控制器上各自的进程。

用户说“结束成语接龙”“不想玩了”等退出意图即可退出整个应用。每题有 30 秒有效回答时间，模型处理与机器人自己的播报暂停答题计时；第 10、20 秒提醒接字。第 30 秒可以使用本局仅一次的援助，示范合法答案后机器人继续接词，援助不计分；机会已用仍超时则本局输。援助生成失败不伪造答案、不扣错误次数，保留一次正常答题窗口。

原厂 IDLE 不结束应用：进行中的题目仍保留；局间唤醒后说“继续”或“再来一局”开始新挑战。唤醒和提示不重置应用的 120 秒无有效回应期限。输了或通关后仍由游戏监听，直到明确退出或应用超时。

游戏独占期间由游戏进程自己订阅和识别语音，Buddy 暂停语音处理，只监督进程与清理。游戏仅接受原厂 `LISTENING` 状态下新开始并完整结束的 VAD 语句；`SPEAKING`、IDLE 和其他状态下的音频、跨状态残句均丢弃。有源时间戳时，还会丢弃早于本次 LISTENING 窗口的迟到包；时间戳为零时按到达时的状态和 VAD 边界判断。唤醒时请等原厂应答结束再说答案；连续说“Q仔，Q仔，一马当先”且答案与唤醒应答重叠时，不作为有效回答。此策略有意放弃应答期间的用户插话，状态过滤本身不代表已验证所有回声均被消除。正常退出或异常退出都先清理自己的资源，再由 Buddy 恢复后续语音处理。

期限前已开始的完整语句可获得最多 18 秒有界收尾；完整录音的 ASR 与意图判定共用一次最多 30 秒预算，不能分别叠加等待。可理解的回答、解释、求助或调级会刷新应用无回应期限，并在回复播完后重新给 30 秒回答；空识别、噪声、不确定和失败重试保留应用期限，不能无限续命。已收到候选语句时允许上述一次处理宽限，未能确认且原期限已过则直接结束。其他模型处理有独立上限，等待模型时持续接收 ROS 状态；迟到结果在关闭后不能再发声或运动。输入录音只在内存中处理，不保存儿童语音。

全部播报走原厂 PlayMediaFile，按自己的 trace 确认真实结束，再立即开收音窗；文件清理随后完成。120 秒无有效回应直接使用缓存结束语，清理后交还 Buddy，不再等待一次云 TTS。120 秒是退出触发期限；已经提交的音频/动作仍须确认结束和清理，不能保证该秒已完全交还。传输后以及实际提交播放前再次检查期限，过期不提交新的自动提示。原厂播放/动作终态未知时保留恢复记录，不能仅凭停止请求成功声称结束。

## 庆祝动作

普通答对只播放开心表情；明确识别为真实成语但首音不符时只播放难过表情。没听清、判断不确定或非成语不触发答错反馈，也不增加错误次数。达到本级目标获胜时播放开心表情并执行已启用、已验收的庆祝动作；三次答错或用完援助后超时判负时播放难过表情并执行已验收的失望动作。普通答题即使开启动作也不驱动身体。

默认 `celebration.enabled=true`，T1 开心/难过表情分别为 90/21，结束后复位为 13；Q1 开心/难过为 3003/3018、复位为 3001。Q1 的 3018 已在当前固件 `q1/emotions.yaml` 核实为 `SAD_EXPRESSION`，旧 SDK 表格未收录。Q1 尚未找到已核对的失望身体动作，失败时保留难过表情及语音鼓励，身体动作返回不可用，不使用拒绝或其他动作代替。表情单次播放，服务响应只说明请求被接受，视觉效果仍须现场确认。

T1 的开心/难过资源各约4秒，程序在接受后预留5秒完整播放再复位，避免短时庆祝把动画提前截断。身体动作单独计时，四足开心仍最多2秒并先归位，再等表情结束；取消和故障直接进入清理，不等待完整表情。

T1 和 Q1 表情均通过原厂 ROS `PlayEmotion` 服务调用，不使用 HTTP 表情入口或 HTTP 回退。预检查失败不发送表情，提交后结果未知保留记录且不重发。T1 的冷客户端首次请求偶发无回复问题仍待实机定位；不能以单元测试或改换协议当作该故障已经修复。只读复现工具为 `tests/manual/ros_service_probe.py`，它只查询 `GetMotionList`，记录冷客户端首个和后续请求，不播放表情或身体动作。

实体动作默认关闭。保存下次开局的设置使用 `python3 main.py motion on` / `motion off`，`motion status` 查看；这些命令不立即驱动机器人。Buddy 安装时须显式指定该游戏的私有配置路径，避免改到独立运行的另一份设置：

```bash
python3 ~/.primebuddy/skills/chengyu-chain/main.py \
  --config ~/.primebuddy/cfg/skills/chengyu-chain/config.yaml \
  --data-dir ~/.primebuddy/data/chengyu-chain \
  --runtime-dir ~/.primebuddy/runtime/chengyu-chain motion on
```

`play --motion on` / `play --motion off` 只覆盖本次运行；打开动作不等于完成现场验收。验收必须确认当前设备身份、现场条件、轨迹幅度、实际时长、自然结束、取消和归位，再在游戏自己的私有配置中设置 `commissioned=true`、匹配 `commissioned_for.series/sku`，分别填写以下验收项：

| 配置项 | 验收内容 |
| --- | --- |
| `verified.T1_biped/T1_quad/Q1` | 对应型号及形态的开心动作 |
| `verified_sad.T1_biped/T1_quad` | 对应形态的难过动作；与开心验收分开 |
| `verified_stand.T1_quad` | 已确认四足坐/趴姿经原厂高层任务准备站立 |
| `verified_step.T1_quad` | 当前固件要求经过原地踏步模式时，完整开心、取消和返回路径已验收 |

四足开心路径读取当前 MC 进程实际加载的 `action_ruler.yaml`，只允许站立、原地踏步、开心及返回这几个模式。部分 T1 固件需要 `101/102 → 121 → 114`；从 101 开始须经 `114 → 121 → 101` 返回，从 102 开始可 `114 → 102` 返回。程序逐步核对同一任务的实时模式、运行状态与允许切换反馈，不能用旧 SDK 示例或“请求已接受”代替完成切换。未验收中间踏步路径时不会因已有开心验收标记而自动执行。

当前 T1 的开心动作也可能自行结束到102。程序检查该任务仍属于本次游戏，并验证从102回到开局姿态的路径；不会为归位重新播放开心动作。切换期间短暂出现未定义状态时只做有界观察，只有双方反馈均为RUNNING且允许切换后才提交下一步控制。

这些项默认均为 false。未验收的动作返回具体不可用原因，游戏可以继续语音和已支持的表情；LLM、游戏话语及 CLI 动作开关不会自行写入验收标记。

开心候选为 T1 双足 `BOTH_HANDS_ACTION_HAPPY`、四足 `QUADRUPED_LOCOMOTION_PLEASURE`、Q1 `Q_SHOW_HAPPINESS`。难过候选为 T1 双足 `HUMANOID_SAD` 和四足 `QUAD_MIMIC_SAD`。双足预设必须由运行时符号匹配 SDK 文档的 2033 并核对资源，缺少符号时不裸发数字；四足必须核对 `SetMcMotion` 字段、执行枚举、原厂同名资源及自由中断属性。预设等待自有任务的运行→完成；四足 Mimic 等待自有任务进入 Mimic，再自然返回本形态稳定站立，取消时仅停止仍由本任务拥有的动作。

动作准备检查新鲜运控及 BMS、未充电/未接充电器、静止、未跌倒、未提起/抱持，以及任务归属和当前形态。只读查询必须明确返回关节供电 ON，且每次身体控制写入前重新查询；不会自动开启关节供电。已稳定站立时保持双足/四足形态。

游戏启动时，启用动作且已完成站立准备验收的 T1 如果正处于四足趴卧/坐姿（110/111），先播报“请确认四周安全，我要站起来了。”，等实际播放结束后自动请求原厂站立（101），确认连续站稳后才开始出题；无需用户再用 App 起身或额外回答一次。已经站立或关闭动作时不播报、不重复起身。提示播放失败或取消不会发送站立请求，提示期间有外部控制接管也不会覆盖。只观察原厂站立任务内部的恢复/准备/踏步过渡，不向这些中间模式另发起身请求；只有稳定站立的 RUNNING 反馈才算完成。游戏中获胜或判负触发身体反馈不会再从趴姿静默起身，结束后保持站立。

PASSIVE、未知姿态和 Q1 未核对的坐姿转换不会被当作正常坐姿强行起身。检查未通过且尚未提交实体控制时可继续语音；已提交任务结果未知时结束应用、保留恢复记录并阻止交还。原厂拒绝或外部接管时不重发、不覆盖。

以上为候选资源及本地协议实现，不代表已完成本轮实体动作验收；尤其不能根据动作名称推断幅度足够小，或根据服务成功响应推断关节已经运动。

## 检查与恢复

```bash
python3 main.py status
python3 main.py recover
python3 main.py play --simulate
python3 -m unittest discover -s tests -v
```

`status` 只检查进程锁和本应用恢复记录。`recover` 只处理自己的已记录媒体、动作和模式，不删除未知状态记录来放行。独立模式恢复可能启停原厂 Agent，动作恢复也必须遵守现场操作要求；宿主隔离时不得绕过检查强制恢复监听。

`play --simulate` 使用虚拟时钟、模型和设备，运行同一会话逻辑，不连接云服务或机器人。命令 stdout 为 JSON，诊断走 stderr；退出码 0 表示该命令完成，`resources_released` 单独表示本应用已知资源是否清理完毕。

本版通过 316 项单元测试。Q1 已使用合成语音文件验证初级 5 次获胜、进入中级、退出交还 Buddy，以及静音不重复报错；单次开心摆臂、表情和自然归位也已获现场确认。难过表情及复位有显示状态反馈，尚未取得人工观感确认。修复后的真人麦克风路径、中高级通关、游戏内晋级身体联动、动作中途取消，以及 T1 双足/四足的当前版本验收仍待完成；文件输入测试不代表声学准确率已经验收。

## Buddy 技能安装协议 v1（开发约束）

新平台技能在 `cfg/pkg.yaml` 声明 `primebuddy.version: 1`，并必须提供 `primebuddy.cli.configure`。这是统一入口；不要求所有作者使用同一个文件名，作者可自行实现交互向导。例如：

```yaml
primebuddy:
  version: 1
  mode: task  # 多轮独占应用使用 exclusive
  cli:
    configure: [main.py, --config, '{config}', --data-dir, '{data}', --runtime-dir, '{runtime}', configure]
```

- `configure` 是非空参数列表，第一项必须是技能包内实际存在的脚本；不得越界、使用 shell 拼接命令或动态生成脚本路径。缺少入口、文件不存在、参数模板非法或协议不受支持时拒绝安装该协议包。
- Buddy 在子进程中调用作者的向导，并传入该技能专属的配置、持久数据和运行时路径。向导自行呈现问题、保存配置和验证；成功退出码为 0，失败或取消返回非 0。即使无需配置，也须提供可成功退出的入口。
- 向导须可重复运行，保留已有配置和登录态，取消后不得伪装成成功；不在安装阶段起身或执行身体动作。新装配置失败会保留待配置文件但不启用；替换现有版本时配置失败回滚旧安装。平台未勾选的技能不会执行向导或安装依赖。
- 协议包以自身 CLI 声明为准，不受 Buddy 内置旧技能映射覆盖；用户 `cfg/skill-adapters.yaml` 的显式覆盖仍优先，但须保留配置入口。独占应用还须提供 `status`、`recover` 和前台启动动作，并遵循资源释放约定。
- 技能通过 CLI 和文件交换数据，不导入 Buddy 内部 Python 模块。配置和持久数据保存在传入目录中，不写入随升级替换的源码目录；依赖固定在技能自己的 `requirements.txt`，由平台隔离安装到技能 `_deps`。
- `primebuddy.version` 表示宿主交互契约，独立于包顶层的业务 `version`。Buddy 的兼容升级应继续支持 v1；破坏参数、退出码或资源管理语义时必须引入新协议并提供迁移路径。已安装的旧文档技能、旧 setup/适配器继续兼容；正式发行内置技能必须采用 v1，新技能不要依赖旧适配器。

平台升级保留兼容技能的代码、配置和数据，不因 `recommended_version` 更高就替换。未安装技能保持未安装。目标平台不兼容的托管官方技能仍按清单执行事务性配套更新；外部目录不被覆盖，不兼容的启用技能会阻止升级。主动更新兼容技能可在 `primebuddy onboard` 中勾选随包新版本，或用 `primebuddy skill install <包> --replace` 调用其向导。协议兼容不代表不同机器人固件或外部服务已自动通过验收。


### 机载 SDK 与机型适配

T1/Q1 统一使用 `/robot/software/interface/aimdk_msgs` 的 Python 消息、类型支持动态库和包环境钩子；标准包缺失时明确失败，不加载 housekeeper/app_proxy 的副本。独立 `python3 main.py` 与 Buddy 托管启动遵守同一规则。

动作分别选择 Q1、T1 双足和 T1 四足策略，不自动切换双足/四足。T1 双足 201 是过渡到稳定控制 300 的入口，结束后保持 300；四足保持原四足形态。T1 资源查询显式指定形态；已核对的命名 Mimic 可接受资源类型 `NONE=0` 或 `MIMIC=2`，仍须存在且允许打断，其他类型拒绝。

资源查询通过不代表已完成实体动作验收。未知任务结果不重发；检测到外部任务接管时不强制恢复。身体动作须在有人看护、场地和姿态适合时按机型分别验证。

T1 双足难过 `2033` 在运行时常量缺失时，仍须在双足资源列表中核对；若常量存在但值不符则拒绝。T1 的 `DEFAULT_POS=0` 作为复位命令校验，不要求出现在动作资源列表；Q1 仍核对枚举出的复位资源。当前形态的验收标记不会授权另一形态。
